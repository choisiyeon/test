## 3. 시나리오 상세 (Given-When-Then)

### AC-02-01 접수 → 작업중  `정상` `E2E`

```gherkin
Scenario: 접수 → 작업중
  Given 직원으로 로그인되어 있다
    And 접수 A의 상태가 "접수"다
  When 접수 목록에서 접수 A의 [작업 시작]을 누른다
  Then 접수 A의 상태가 "작업중"으로 바뀐다
    And 상태 변경 이력에 "접수 → 작업중", 변경자 "staff01", 변경 일시가 기록된다
```

### AC-02-02 작업중 → 완료, 완료 일시와 알림 이벤트 기록  `정상` `통합`

```gherkin
Scenario: 작업중 → 완료, 완료 일시와 알림 이벤트 기록
  Given 접수 B의 상태가 "작업중"이다
  When 직원이 [작업 완료]를 누른다
  Then 상태가 "완료"로 바뀐다
    And 완료 일시가 기록된다
    And 완료 알림용 이벤트(ORDER_DONE) 1건이 저장된다
```

### AC-02-03 단계 건너뛰기 불가  `입력 검증` `단위·통합`

```gherkin
Scenario: 단계 건너뛰기 불가
  Given 접수 A의 상태가 "접수"다
  When 상태를 "완료"로 바로 변경하도록 API를 요청한다
  Then 422 응답(INVALID_TRANSITION)이 반환되고 상태는 "접수"로 유지된다
```

### AC-02-04 직원의 되돌리기 차단  `권한` `E2E·통합`

```gherkin
Scenario: 직원의 되돌리기 차단
  Given 직원으로 로그인되어 있다
    And 접수 C의 상태가 "완료"다
  When 접수 상세 화면을 연다
  Then [이전 단계로] 버튼이 보이지 않는다
  When 직원 계정으로 "작업중" 되돌리기 API를 요청한다
  Then 403 응답이 반환되고 상태는 "완료"로 유지된다
```

### AC-02-05 관리자의 되돌리기와 사유 기록  `정상` `E2E`

```gherkin
Scenario: 관리자의 되돌리기와 사유 기록
  Given 관리자로 로그인되어 있다
    And 접수 C의 상태가 "완료"다
  When [이전 단계로]를 누르고 사유 "수선 부위 재작업"을 입력해 확인한다
  Then 상태가 "작업중"으로 바뀐다
    And 완료 일시가 지워진다
    And 상태 변경 이력에 사유 "수선 부위 재작업"이 표시된다
```

### AC-02-06 되돌리기 사유 누락 거부  `입력 검증` `통합`

```gherkin
Scenario: 되돌리기 사유 누락 거부
  Given 관리자로 로그인되어 있다
  When 사유 없이 되돌리기 API를 요청한다
  Then 422 응답이 반환되고 상태가 바뀌지 않는다
```

### AC-02-07 동시 변경 시 나중 요청 거부  `예외` `통합·E2E`

```gherkin
Scenario: 동시 변경 시 나중 요청 거부
  Given 직원 2명이 같은 접수 B 화면을 열어 둔 상태다
  When 첫 번째 직원이 [작업 완료]를 누르고, 이어서 두 번째 직원이 같은 버튼을 누른다
  Then 두 번째 요청은 "다른 사용자가 이미 변경한 건입니다" 안내와 함께 거부된다
    And 화면이 최신 상태로 새로고침된다
    And 상태 변경 이력은 1건만 추가된다
```
