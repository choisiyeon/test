---

## 1. 요약

- 접수 1건당 사진 여러 장 첨부, 접수 등록 중 또는 등록 후 상세 화면에서 추가
- 업로드 시 서버에서 크기 축소·위치정보(EXIF(사진 촬영 정보)) 제거 후 저장
- 저장소는 S3 호환 객체 저장소(MinIO)를 사용해 클라우드·매장 PC 어디서든 동일하게 운영
- 사진 삭제는 관리자만, 직원은 추가·조회만 가능

---

## 2. 인수 조건 (스토리 기준 초안)

1. 접수 화면에서 사진을 선택하면 미리보기가 표시되고, 접수 저장 시 함께 저장된다.
2. 접수 상세 화면에서 사진을 추가로 첨부할 수 있다.
3. 허용되지 않은 파일 형식이나 용량 초과 파일을 선택하면 안내가 표시되고 업로드되지 않는다.
4. 사진을 누르면 크게 볼 수 있다.
5. 직원에게는 사진 삭제 버튼이 보이지 않으며, 관리자는 삭제할 수 있다.
6. 사진 업로드가 실패해도 접수 정보는 저장되고, 상세 화면에서 다시 올릴 수 있다.

---

## 3. 기술 선택

| 구분 | 선택 | 이유 |
| --- | --- | --- |
| 저장소 | MinIO(S3 호환), Docker Compose에 추가 | DB에 이미지 저장 시 용량·백업 부담, 클라우드 이전 시 S3로 그대로 전환 |
| 업로드 방식 | 서버 경유 업로드(Next.js Route Handler) | 축소·검증을 서버에서 일괄 처리, 매장 규모에 충분 |
| 이미지 처리 | sharp | 크기 축소, JPEG/WebP 변환, EXIF 제거 |
| 조회 | 서버가 발급하는 만료형 URL(서명 URL) | 로그인한 사용자만 사진 열람 |

### 제안 기준값 (매장 확인 후 확정)

| 항목 | 제안값 | 비고 |
| --- | --- | --- |
| 허용 형식 | JPEG, PNG, HEIC, WebP | 휴대폰 촬영 사진 고려 |
| 원본 최대 용량 | 10MB/장 | 초과 시 업로드 거부 |
| 건당 최대 장수 | 5장 | |
| 저장 크기 | 긴 변 1600px, 썸네일 긴 변 320px | |
| 서명 URL 유효시간 | 10분 | |

## 4. 데이터 모델 변경

```prisma
model OrderPhoto {                     // D-07 사진
  id           String   @id @default(cuid())
  orderId      String
  order        Order    @relation(fields: [orderId], references: [id])
  storageKey   String                  // 예: orders/20261125-007/<cuid>.webp
  thumbKey     String
  width        Int
  height       Int
  sizeBytes    Int
  uploadedById String
  createdAt    DateTime @default(now())
  deletedAt    DateTime?               // 삭제 시 즉시 지우지 않고 표시(복구 대비)
  deletedById  String?
  @@index([orderId])
}

model Order {
  // ...기존 항목 유지
  photos OrderPhoto[]
}
```

## 5. API 설계

| 메서드 | 경로 | 설명 | 권한 |
| --- | --- | --- | --- |
| POST | `/api/orders/:id/photos` | 사진 업로드(multipart, 여러 장) | 관리자·직원 |
| GET | `/api/orders/:id/photos` | 사진 목록 + 썸네일·원본 서명 URL | 관리자·직원 |
| DELETE | `/api/orders/:id/photos/:photoId` | 사진 삭제(삭제 표시) | 관리자 |

### 업로드 처리 순서

1. 로그인·접수 존재 확인, 현재 장수 + 요청 장수가 최대 장수 이하인지 확인
2. 파일별 형식 확인(확장자가 아닌 파일 내용 기준), 용량 확인 → 위반 시 해당 파일만 거부 사유 반환
3. sharp로 회전 보정 → EXIF 제거 → 원본(1600px)·썸네일(320px) WebP 생성
4. MinIO 저장 → DB에 OrderPhoto 저장(저장 실패 시 MinIO 파일 정리)
5. 결과 반환

```json
// 응답 207 (일부 성공)
{
  "saved": [{ "id": "ck...", "thumbUrl": "https://..." }],
  "rejected": [{ "fileName": "IMG_0012.mov", "reason": "허용되지 않는 형식입니다" }]
}
```

### 접수 화면과의 연결

- 접수 화면에서 선택한 사진은 브라우저에 임시 보관 → 접수 저장(US-01 API) 성공 후 받은 접수 id로 업로드 API 호출
- 업로드 실패 시 접수는 유지, 상세 화면으로 이동하며 "사진 업로드 실패, 다시 첨부하세요" 안내(인수 조건 6)

## 6. 화면

### S-03 수선 접수 (항목 추가)

```
사진  [ 📷 사진 추가 ]  (최대 5장, 장당 10MB)
      [썸네일][썸네일][ × ]   ← 저장 전에는 선택 취소 가능
```

- PC 웹 기준 파일 선택 창, 매장 PC에 웹캠이 있으면 촬영 입력 지원 여부는 2차 검토

### 접수 상세 (영역 추가)

- 썸네일 목록, 클릭 시 크게 보기(좌우 넘김)
- [사진 추가] 버튼, 관리자에게만 썸네일별 [삭제]

## 7. 보안·개인정보

- 사진 URL은 로그인 사용자에게만 서명 URL로 발급, 외부 공유 링크 없음
- EXIF 제거로 촬영 위치·기기 정보 저장 방지
- 사진에 얼굴 등 개인정보가 포함될 수 있으므로 의류만 촬영하도록 화면에 안내 문구 표시
- 보관 기간(출고 후 며칠 뒤 삭제할지)은 결정 필요사항, 확정 시 정기 삭제 작업 추가

## 9. 인수 조건 ↔ 테스트 매핑

| 인수 조건 | 테스트 |
| --- | --- |
| 1. 접수 시 미리보기·함께 저장 | E2E: 사진 2장 선택 → 미리보기 2개 → 저장 후 상세에 썸네일 2개 |
| 2. 상세에서 추가 첨부 | E2E: 상세 [사진 추가] 후 썸네일 증가 |
| 3. 형식·용량 위반 거부 | 통합: .mov 파일, 10MB 초과 파일 → rejected 사유 반환, DB 미저장 |
| 4. 크게 보기 | E2E: 썸네일 클릭 시 확대 창 표시 |
| 5. 삭제 권한 | E2E: 직원 화면에 [삭제] 없음 / API: 직원 요청 403, 관리자 요청 후 목록에서 제외 |
| 6. 업로드 실패 시 접수 유지 | 통합: 저장소 오류 상황에서 접수 저장 성공, 사진 0건 / E2E: 실패 안내 표시 |
| EXIF 제거 | 단위: GPS 정보가 있는 샘플 처리 후 EXIF 없음 |
